## 1. Pipeline handlers (register them on the existing `Orchestrator` with `register(kind, handler)`; a `pipeline/handlers.py` exposing `register_all(orchestrator, deps)` and a `Dependencies` dataclass of ports/services)
Every job has a deterministic idempotency key so retries, restarts and double scheduling never duplicate work.
1. **`collect`** (worker `collector`; queue urgent for hot sources, else normal). Payload `{source_id}`. Load the `Source`, build the connector from `connectors.registry`, call it through the existing ingest `collect` flow if available via the port you are given (otherwise `connector.fetch` + `IngestPort.ingest`), then for every new item enqueue `process_item` with key `process:<raw_item_id>`. A `ConnectorError` fails the job as transient with the real (credential-free) message; never fabricate items.
2. **`process_item`** (worker `local`). Payload `{raw_item_id}`: `ClusterPort.assign(raw_item_id)`; `BriefStore.create(raw_item_id=…)` then `advance` to `PREPROCESSED` then `PROCESSING`; enqueue `draft_brief` with key `draft:<brief_id>:rev0` and payload `{brief_id, raw_item_id, feedback: null}`. Idempotent: if a brief already exists for the raw item (query `briefs.raw_item_id` read-only), reuse it instead of creating another.
3. **`draft_brief`** (worker `gemini`). Payload `{brief_id, raw_item_id, feedback}`: `items = ClusterPort.related_items(raw_item_id)`; `scores = RuleScorer(...).score(items)`; `draft = await GeminiBriefDrafter(ai_worker).draft(items, scores, feedback=feedback)`; `BriefStore.submit_draft(brief_id, draft, expected_revision=<current revision_count>)`. If the brief is already `PENDING_CLAUDE_REVIEW` (retry after the submit succeeded) → succeed without redrafting. AI statuses are mapped by the orchestrator already; a validation `ValueError` from the drafter is a transient failure (retry), then dead.
4. **Revision loop** — `watch_revisions()` (called by the scheduler tick): for each brief in `REVISION_REQUIRED` that has no queued/running `draft_brief` for its next revision: `BriefStore.advance(brief_id, PROCESSING)` (this opens the next revision), then enqueue `draft_brief` key `draft:<brief_id>:rev<N>` with `feedback` = the reason of the latest review decision (`BriefStore.detail(...).review_history[-1].reason`). Never exceeds 2 revisions (the state machine enforces it; do not duplicate the rule).
5. **No approval logic anywhere.** Claude unavailable ⇒ briefs simply stay `PENDING_CLAUDE_REVIEW`; nothing in this task approves, rejects or sends alerts.
Reads of ids not exposed by services (e.g. `briefs.raw_item_id`, finding REVISION_REQUIRED rows) may use small read-only SQL in `pipeline/queries.py`; ALL state changes go through `BriefStore`/`PersistentQueue`.

## 2. Adaptive scheduler (idead.md §5)
- `scheduler/policy.py` (pure, deterministic, injectable clock/random): source classes by `Source.priority` bands → `hot_news` (≥ 90), `trending` (70–89), `priority_creator` (50–69), `normal` (20–49), `low_activity` (< 20). Base intervals come from the dashboard preference `scan_intervals_minutes` (read via `OperationsService.preferences()`; keys are the class names; sensible defaults 10 / 30 / 60 / 180 / 720 minutes if a key is missing). Adaptive rules: halve the interval (never below the class minimum = 50% of base) after scans that produced new items with strong signals; lengthen ×1.5 (cap = 4× base) after empty scans; exponential backoff with jitter after errors; `BLOCKED`/`UNAVAILABLE` connector health ⇒ stop scheduling that source until its backoff expires; honour a `retry_after` seconds value when the connector error carries one; ±10% jitter. Document the numbers as initial, configurable constants.
- `scheduler/service.py`: `Scheduler.tick(now)` decides which enabled, non-blocked sources are due and enqueues `collect` jobs with key `collect:<source_id>:<slot>` where `slot` is the interval slot number (so a restart or two ticks in one slot never double-scan). Hot sources and sources with rising growth go to the urgent queue. It also calls `watch_revisions()` each tick. Last-scan state is derived from persisted data (connector health `last_success_at` / job history), NOT from memory, so a restart resumes correctly; on startup perform at most ONE catch-up scan per source. Skip enqueueing while the injected resource gate says the machine is loaded.
- Admin-driven learning from feedback is OUT of scope (later phase).
