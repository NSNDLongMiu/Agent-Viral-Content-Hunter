## Problem (measured on a real run)
The pipeline drafts a brief with Gemini for EVERY collected item: one scan of 3 sources queued 108 `draft_brief` jobs in 20 s (about 15 minutes of AI time at 2 slots), wasting the user's subscription quota on weak items. The deterministic `RuleScorer` runs for free before drafting. Measured on 109 real items: priorities P3=108, P2=1, P1=0; virality median 50-67 (max 80); relevance median 33-63 (max 70); credibility 35 for nearly all. So "P2 or better only" would let ~1 item through: NOT acceptable. Use signal thresholds plus a cap.

## Work
1. `pipeline/gate.py`: frozen dataclass `DraftGate(min_virality: float = 60.0, min_relevance: float = 45.0, max_per_scan: int = 8)`, validated in `__post_init__` (scores finite and within 0..100, `max_per_scan >= 1`, else `ValueError`). A scored item is ELIGIBLE if its priority is P1 or P2, OR (virality >= min_virality AND relevance >= min_relevance). Provide `select(candidates)` taking `(raw_item_id, ScoringResult)` pairs and returning the chosen ids: eligible only, ranked by priority (P1 > P2 > P3) then by virality+relevance descending, tie-break by `raw_item_id`, truncated to `max_per_scan`. Deterministic, pure.
2. `handlers.py`: `Dependencies` gets `gate: DraftGate = DraftGate()`. In the `collect` handler, AFTER ingest returns the new item ids: call `ClusterPort.assign` for ALL new items first (so cross-source corroboration is visible), then score each new item with `ClusterPort.related_items` + the scorer, apply the gate, and enqueue `process_item` ONLY for the selected items (same key `process:<raw_item_id>`). Unselected items stay stored as raw evidence with no brief and no AI call. `process_item` keeps calling `assign` (idempotent). Keep counts on the `Pipeline` (for example `last_scan: dict[str, ScanStats]` with collected/new/eligible/selected/skipped) — counts only, never titles or URLs.
3. `config.py` `[runtime]`: add `draft_min_virality` (60.0), `draft_min_relevance` (45.0), `max_drafts_per_scan` (8) with validation; env overrides in the existing `HUNTER_RUNTIME__...` style; update `config/settings.example.toml` and `docs/CONFIGURATION.md` (Vietnamese: why — tiết kiệm quota, ưu tiên chất lượng). `runtime/service.py` passes them into `Dependencies(gate=...)` and logs one INFO line per scan with the counts.
4. Document in `docs/CONFIGURATION.md`: an item skipped now is deduplicated on later scans, so a later rise in its metrics is not re-evaluated in this MVP (emerging-viral detection with a second snapshot is a later phase).
5. Tests: gate validation; eligibility rule incl. boundary values; cap and ordering deterministic; unselected items get no `process_item` job and no brief; selected items enqueued exactly once even if collect runs twice; clustering happens before scoring (an item that passes only thanks to cluster evidence is selected); config defaults/validation/env override; runtime passes the config into `Dependencies`. Existing tests must keep passing — if an existing test assumed every new item is processed, update it so it uses a fake scorer or gate that selects everything, not weaker assertions.
